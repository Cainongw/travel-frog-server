# 实现范围与后续工作

本文以当前服务端与 `admin-ui/src` 为准。开发版本为 0.12.0；集群部署与原生验收进度见 [复刻路线](replication-roadmap.md)。SQLite 游戏 schema 与 JSON 导出格式为 v6，仍接受 v1–v5 导入；管理快照另有带完整性校验的内部格式。客户端能打开页面或收到成功回包，不能单独证明玩法已完整验证。

APK 配置包含图片、物品、笔记和奖项定义，不能据此恢复玩家的官方账号进度。管理台管理的是当前服务器的 SQLite 数据；将真实存档迁入仍需先取得真实数据，再转换成相应记录。

## 本轮修正的客户端语义

### 访客离场时间不是礼物失效时间

APK 的 `MainOutView.updateVisitorGift()` 在 `expire_time <= serverTime` 时显示礼物；在此之前显示访客。服务器因此保留已离开的访客记录，直到 `visit.open` 领取礼物，而不是在该时间删除记录。未到离场时间的领取请求被拒绝；领奖后进入下一次来访等待期。

后台“访客离场”把当前访客的离场时间提前到现在，不直接发奖。奖励仍由游戏端 `visit.open` 触发。后台账号查询和导出不会顺便生成新访客。

### 明信片邮件打开后需要完整的新图片列表

`TravelModel.album_load_new` 会替换客户端的待收图片数组，并非追加一张图片。`mail.open` 后只推这封邮件的图片会把其他待收图片从客户端内存中暂时移除。因此服务器推送账号的全部 `new` 图片，已保存到相册的图片不在该列表中。

管理端图片下发在同一事务内写入图片记录、对应邮件和操作记录，再通知已经同步的在线游戏连接；离线账号的记录留在数据库，下一次登录同步即可读取。下发本身不等于玩家已点击保存，保存仍使用 `album.save_new`。

### 奖励更新必须发绝对余额

已分析版本中 `UserModel.addTicket` 和 `ItemModel.addHouseItem` 是空函数，`consumeTicket` 也只检查余额。不能以“客户端源码写了 addTicket 调用”为由省略服务端推送。服务器发 `item_update_ticket` 的绝对券余额，以及 `item_update` 的绝对库存数量。访客、邮件和兑奖结算均需遵守该约定。

`item.gacha` 的回包字段 `ticket` 则表示颜色编号 0–5，不是券余额。它有 session 回包，自动触发客户端抽奖事件，不应再推送同名事件播放第二次。

## Svelte 管理台与管理 API

v0.10 增加独立管理 Docker 镜像/Deployment/Service，保留原公网管理路径；独立账号管理页支持登录名与存档关联、创建、密码重置、禁用、撤销会话、删除登录名并保留存档。Android 原生登录 Activity 保存续期凭据，在 30 天不活跃期限内自动恢复，替换每次打开都输入密码的游戏画布表单。账号管理、续期与审计表不随游戏快照回档。见 [native-login.md](native-login.md)。

v0.9 增加 Authentik/OIDC 管理登录（授权码、PKCE、nonce、签名验证、用户组授权、HttpOnly Cookie、CSRF）与游戏账号密码（scrypt、限频、24 小时随机令牌）。部署模式强制密码登录；默认本地开发仍兼容 TestChannel 和管理密钥。OAuth 会话、凭据、游戏令牌属于认证数据，不进入账号快照或导出。单副本 Docker/k8s 部署及接入说明见 [deployment.md](deployment.md)。

v0.8 新增手动账号快照与回档。`snapshots.js` 保存全部账号游戏表的原始行，并且直接事务恢复，不通过会填充默认值的普通 JSON 导入器。官方保全快照同样支持。恢复前保存当前状态的保护快照；恢复后在线连接失效，需重新连接。快照、管理审计和幂等历史不会被恢复过程删除。定时快照、删除/保留策略与全服务器配置快照不在本版范围。

官方保全账号创建快照后自动进入 `active` 模式，已有快照可通过 `archive-activate` 启用。已有玩法读取和更新当前 SQLite 游戏表，原始采集记录仍完整保留；未实现的模块可展示原始记录，但不能继续结算。缺少本地旅行计时记录的官方旅行/聚会状态切回在家，不编造收益。回档到旧保全快照后同样启用玩法，保持可测试状态。快照创建/模式切换与审计在同一事务内，启用后旧客户端连接失效，需重进。

`protocol_diagnostics.js` 将未实现请求、仅原始快照读取及保全只读拒绝聚合到 `admin_unsupported_calls`，按账号/协议/原因记录次数、首次及最近时间、脱敏参数摘要。管理台“操作记录”展示最近 200 类日志，也可通过 `GET /api/admin/unsupported` 查看。日志不受回档影响；客户端不发送请求的本地操作无法由服务器记录。

前端位于 `admin-ui`，构建后通过 `/admin/` 提供。`/api/admin/*` 与游戏 WebSocket 共用 Node 服务，但使用不同访问规则。

已接入账号选择/创建、在线状态、账号数据查看，模板与图层 JSON 明信片预览/下发，草/券/道具奖励邮件，角色姓名/余额调整，天气修改，旅行笔记解锁，访客离场，JSON 导入导出、操作记录与覆盖前备份下载。

v0.7 新增庭院页：工作台物品放入/取出、配方缺额补给邮件、制作任务查询/提前完成、已有家具摆放、商店购买、邻居到访与离场。`GET /api/admin/garden` 只读；各写操作有审计和幂等键。原生商店和工作台回包后的客户端还有本地修改，因此服务器先回复 session，再推完整状态。邻居在线变化在 `guest_load` 后推 `client_load_role`，触发庭院重绘。详细证据见 [furniture-protocol.md](furniture-protocol.md)、[neighbors-protocol.md](neighbors-protocol.md)；REA 的部分静态分析边界见 [rea-evidence.md](rea-evidence.md)。

- 管理接口使用至少 24 字符的 `FROG_ADMIN_TOKEN` Bearer 密钥。未配置时管理接口返回 503；配置后旧 `/api/*` 接口也要求密钥，旧导入/天气写接口引导使用有审计的管理接口。
- 管理写请求使用 `Idempotency-Key`。同一编号和相同操作重试返回原结果，不重复发图片、邮件或奖励；编号被用于不同操作时拒绝。前端对未明确成功的网络重试复用编号。
- 明信片 ID、资源 ID、图层坐标、物品 ID 和部分存档字段对照配置校验。APK 资源缺失时不能凭空生成目录内容；配置不存在的图片和奖项不会伪装为已支持。
- 覆盖导入前保存该账号的 JSON 快照，备份与导入处于事务中。管理操作记录和备份表是服务器管理数据，不随普通账号 JSON 导出迁移。
- 密钥保存在前端内存中，图片通过带鉴权的 fetch 加载，不将密钥放进 URL。当前使用单一管理密钥，没有多管理员账号、角色权限或密钥轮换页面。

### 远程管理与游戏网络隔离

HTTP 管理支持 OIDC 会话或开发用 Bearer 密钥。游戏 WebSocket 默认只接受 loopback 连接；设置 `FROG_ALLOW_REMOTE_GAME=1` 才允许直接远程游戏连接。该开关本身不增加玩家认证；部署示例还设置 `FROG_GAME_AUTH_REQUIRED=1`，要求先通过账号密码取得令牌。

经反向代理部署时，Node 看到的对端可能是代理的 loopback 地址。公网代理应只发布管理台和管理 API，不转发游戏 WebSocket Upgrade。单靠 Node 的远端地址判断不能隔离经同一个本地代理转入的游戏连接。远程管理应使用 HTTPS 或可信隧道，避免在不受信任的网络明文传输管理密钥。

## 明信片模板的还原程度

`travel_data.js` 选择了 APK 中存在的五种场景、青蛙与同行者资源，转换角色坐标，并用手工设置的像素坐标排布背景。客户端与预览都按图层顺序绘制到 500×350 画布。

这些模板是供离线玩法使用的近似排布，不能称为已经恢复官方服务器的完整构图算法。当前没有覆盖全部图片配置的随机背景选择、坐标规则、道具姿态、季节变体或稀有图片概率。管理台可以发送已知合法图层记录，但并不意味着所有 `pic_id` 都已有自动生成模板。原始 PNG 是资源素材，而不是某个玩家拥有那张明信片的证明。

## 本轮新增模块与剩余验证

下列模块已经落地并通过隔离回归，但逐项原生验收尚未全部完成，不能因此将整个路线图勾完：

- `creative.js`：绘画聚会、手作/印章/木片合成、不倒翁、花盆、堆肥、挂兜。[创作说明](creative-protocols.md)
- `activities.js` / `cards.js`：动态照片、扭蛋、许愿池、两类贺卡、蛋糕问答。[活动](activity-protocols.md)与[贺卡蛋糕](card-cake-protocols.md)
- `exploration.js`：博物馆路线、票/收藏/图片与周末挑选。`koto` 只有协议声明，入口仍缺证据。[探索说明](exploration-protocols.md)
- `life.js` / `daily.js`：烹饪任务与月度食品、故事赠礼反馈、日历与清单、新呱奖励、年报、点击特效及美好瞬间。[生活](life-protocols.md)与[日常](daily-protocols.md)
- `progression.js`：103 条配置称号条件、双百科、限期称号道具与过期；长周期以隔离虚拟时间测试。[成长说明](progression.md)
- `postcard_generator.js` / `travel_policy.js`：配置构图与旅行倾向。图层合法不等于所有近似构图都已视觉验收。[明信片](postcard-generation.md)与[旅行](travel-policy.md)

所有新进度位于账号级 `game_module_state`，参与 JSON 导入导出与原始行快照；旧快照没有模块状态时恢复为空，旧捕获仍保留。已知模块导入执行结构/数值校验，拒绝损坏数据；定时推进按模块/账号隔离异常，不应由一份损坏进度终止整个服务。分享/广告/充值与官方 SDK 服务仍不接入；有本地替代的任务明确写在对应说明中。

`server.js` 的默认分支对未实现协议记录日志并返回 `{code:1,supported:false}`，同时发送有限频率的客户端提示。有原始记录的未实现读取协议会返回记录并记为 `snapshot_read_only`。初始化推送中的空数据和原始活动记录不代表相应玩法已经实现。

## 下一步与验证边界

1. 用真实客户端核验新图片邮件、多张待收图片、访客离场礼物以及抽奖动画；协议测试不能替代原客户端的画面和交互验证。
2. 核验家具页、制作锁定/完成提示与原生邻居互动，再实现 `story.*` 赠礼反馈循环。
3. 按独立协议继续恢复手作和花盆等物件，不用已完成的普通家具状态冒充这些玩法。
4. 扩展旅行配置，逐项验证物品消耗性、背包/桌面类别限制、目的地和构图规则；不要以固定轮换模板充当官方完整旅行算法。
5. 根据管理台的未实现功能日志确定后续恢复顺序，并用原客户端逐项复测。

`npm test` 包含存档/基本玩法、管理接口、抽奖、家具和邻居测试；管理 API 测试包含原生工作台/摆放/喂食 WebSocket 往返、鉴权、幂等下发、在线通知、离线交付、导入备份、奖励结算等。快照测试覆盖完整行恢复、损坏拒绝、失败回滚、保全账号启用、回档后继续购买与旅行；诊断测试覆盖累计记录、脱敏与回档保留。`npm run admin:build` 验证 Svelte 编译；前端测试核验网络重试及材料缺额计算。隔离账号的浏览器操作已走通家具制作/摆放与邻居来访。测试通过只能证明其覆盖的行为，不能证明上面列出的未实现玩法或全部原客户端页面已经正常运行。
